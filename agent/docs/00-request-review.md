# بررسی درخواست و شکاف‌های آن

این سند نقد مهندسیِ درخواست اولیه است. هدف آن رد کردن ایده نیست؛ ایده درست
است. هدف این است که قبل از نوشتن یک خط کد، بخش‌هایی که در سناریوی واقعی می‌شکنند
مشخص شوند.

## ۱. آنچه در درخواست درست است

- تفکیک نقش‌ها (محصول، معماری، کدنویسی، QA، امنیت، DevOps) درست است.
- تأکید بر Sandbox، Approval، Audit Log و Least Privilege درست است.
- Modular Monolith برای MVP درست است؛ Microservices از روز اول اشتباه است.
- GitHub App به‌جای PAT عمومی درست است.
- نسخه‌بندی پرامپت‌ها درست است.
- شروع از MVP کوچک و فقط GitHub درست است.
- در نظر گرفتن n8n فقط برای مصارف داخلی و بررسی لایسنس آن درست است.

## ۲. سه شکاف بنیادی

### ۲.۱ «موفقیت» تعریف نشده بود — مهم‌ترین شکاف

در متن اولیه هیچ‌جا مشخص نبود یک تسک بر چه مبنایی «تمام» اعلام می‌شود. در عمل
این بزرگ‌ترین منبع شکست ایجنت‌های کدنویس است: مدل می‌گوید «انجام شد» و هیچ
شواهدی وجود ندارد.

راه‌حل پیاده‌سازی‌شده در این مخزن: **Evidence Rule**. هیچ ادعای موفقیتی پذیرفته
نمی‌شود مگر اینکه به خروجی یک ابزار گره خورده باشد.

`src/core/evidence.ts` تابع `auditCompletionClaim` را پیاده‌سازی می‌کند و این
موارد را رد می‌کند:

| وضعیت | نتیجه |
|---|---|
| `completed` بدون فایل تغییریافته | رد |
| `completed` بدون اجرای هیچ دستور | رد |
| `completed` با دستور exit≠0 | رد |
| `completed` بدون نتیجه تست | رد |
| `completed` با تست fail | رد |
| `completed` با finding بحرانی باز | رد |
| `blocked` بدون دلیل و اقدام بعدی | رد |

این تنها لایه‌ای است که «تقریباً آماده است» را از محصول حذف می‌کند.

### ۲.۲ «کاربر در سایت‌های مورد نظر ثبت‌نام کند» خطرناک‌ترین بخش ایده است

درخواست اولیه می‌گوید کاربر وارد پلتفرم شود و در سایت‌های مورد نظر ثبت‌نام کند
و پلتفرم کار را انجام دهد. این جمله سه مشکل دارد:

1. **ذخیره رمز عبور.** اگر پلتفرم رمز عبور کاربر را در سایت ثالث نگه دارد، به یک
   هدف امنیتی با دامنه آسیب چندبرابر تبدیل می‌شود. یک نشتی = نشتی در N سرویس.
2. **شرایط استفاده سرویس‌ها.** خودکارسازی ورود، دور زدن CAPTCHA و ساخت انبوه حساب
   در اکثر ToS ممنوع است و می‌تواند حساب کاربر را ببندد.
3. **مسئولیت حقوقی.** اگر ایجنت با حساب کاربر کاری انجام دهد که کاربر نخواسته،
   پاسخگویی با کیست؟

معماری جایگزین که در این مخزن طراحی شده:

```
OAuth 2.1 + PKCE  >  Official API Token  >  GitHub App  >  MCP  >  Browser با حضور انسان
```

قاعده: پلتفرم **هرگز** رمز عبور خام را دریافت، ذخیره یا ارسال نمی‌کند. این یک
`deny` سخت در `src/core/policy-engine.ts` است، نه یک توصیه. برای سایت‌های بدون
API، یک مرورگر کنترل‌شده باز می‌شود و **خود کاربر** login، CAPTCHA و MFA را
انجام می‌دهد؛ ایجنت فقط فرم‌های غیرحساس را در دامنه‌های allowlist پر می‌کند.

### ۲.۳ «رایگان» سه هزینه جداست که با هم اشتباه شده بودند

| لایه | رایگان ممکن است؟ | محدودیت واقعی |
|---|---|---|
| مدل زبانی | بله، با مدل محلی | RAM/GPU، سرعت، کیفیت |
| API ابری | بله، با سهمیه | RPM/RPD، سیاست داده، تغییر قوانین |
| اجرای کد | بله، روی دستگاه کاربر | منابع دستگاه، امنیت |
| SaaS چندکاربره | فقط نمونه اولیه | Sandbox و ذخیره‌سازی رایگان نامحدود نیست |

نتیجه معماری: **Local-first + BYOK**. مدل و Runner روی ماشین کاربر؛ API رایگان
به‌عنوان گزینه تکمیلی با نمایش سقف مصرف؛ و Product Key mode برای حالت میزبانی‌شده.
Free Tier باید به‌عنوان «حالت آزمایشی» طراحی شود، نه زیرساخت دائمی — یعنی سیستم
باید وقتی سهمیه تمام شد **بایستد و بگوید چرا**، نه اینکه ساکت شکست بخورد.
`tryConsumeQuota` در `src/core/model-router.ts` همین کار را می‌کند.

## ۳. تناقض‌های درون درخواست

| تناقض | resolution |
|---|---|
| «اتصال به همه سایت‌ها» در برابر «Least Privilege» | کانکتورها مرحله‌ای اضافه می‌شوند؛ MVP فقط GitHub |
| «کاملاً خودکار» در برابر «Deploy با تأیید» | Autonomy Level چهارسطحی؛ کلاس D همیشه تأیید می‌خواهد |
| «رایگان» در برابر «مقیاس تجاری» | دو حالت BYOK و Platform Key |
| «ایجنت همه‌کاره» در برابر «کنترل‌پذیر» | ایجنت‌های تخصصی با یک Task در هر فراخوانی |
| «اجرای موازی» در برابر «بدون Conflict» | قفل فایل + الگوریتم رفع تداخل (`serializeConflicts`) |

## ۴. چیزهایی که در درخواست اولیه غایب بودند

1. **حالت‌های پایانی و شکست.** فهرست حالت‌ها فقط مسیر موفقیت را داشت. `FAILED`،
   `CANCELLED` و `BLOCKED` و قوانین ورود/خروج از آن‌ها اضافه شد.
2. **خروجی از حلقه تعمیر.** `maxRepairAttempts = 3` گفته شده بود اما هیچ حالتی
   برای «تمام شدن بودجه تعمیر» وجود نداشت. `repair_exhausted → BLOCKED` اضافه شد.
3. **الگوریتم رفع تداخل قفل فایل.** ساختار `lockedPaths` تعریف شده بود اما رفتار
   آن در برخورد دو تسک موازی مشخص نبود. پیاده‌سازی شد.
4. **gate ورودی داده به مدل ابری.** فقط گفته شده بود «Secretها Redact شوند».
   سه دروازه لازم بود: redaction، بررسی `mayTrainOnInput`، و رضایت صریح کاربر.
5. **شمارش سهمیه.** Router فقط provider انتخاب می‌کرد؛ حسابداری RPM/RPD نداشت.
6. **اتصال Approval به نسخه Plan.** اگر Plan پس از تأیید تغییر کند، تأیید قبلی
   باید بی‌اعتبار شود. این با hash سند Plan انجام می‌شود.
7. **Idempotency Key** برای Tool Callهای دارای side effect.
8. **انقضای Approval.** یک تأیید بی‌پایان، یک حفره امنیتی است.
9. **نسخه پرامپت در Audit Log.** بدون آن، بازتولید یک Run قدیمی ممکن نیست.
10. **معیار ارزیابی کیفیت پرامپت.** «پرامپت را تست کنید» گفته شده بود اما
    harness آن تعریف نشده بود.
11. **تعریف مرز Control Plane و Execution Plane** در مدل داده.
12. **سیاست حفظ داده و حذف حساب** (GDPR-like) در سطح جداول.

## ۵. اصلاحات مشخص روی طراحی پیشنهادی اولیه

| مورد | متن اولیه | اصلاح شده |
|---|---|---|
| خروجی Orchestrator | یک JSON ثابت | `proposedEvent` اضافه شد تا موتور حالت، نه مدل، انتقال را تصمیم بگیرد |
| Task | بدون معیار پایان ماشینی | `definitionOfDone` و `estimatedTokens` اضافه شد |
| Connector Manifest | بدون سهمیه و محل داده | `rateLimits`، `dataResidency`، `tokenTtlSeconds`، `requiresPkce` اضافه شد |
| ToolCallDecision | بدون scope | `requiredScopes` و `targetRef` اضافه شد |
| Security Finding | بدون اثبات رفع | `verification` الزامی شد |
| QA Report | بدون تفکیک flaky | `flaky` و `flakyTests` اضافه شد |
| Event | بدون نسخه schema | `schemaVersion` با `const: 1` و `redacted` اضافه شد |
| State Machine | فهرست خطی | جدول انتقال + ۶ invariant قابل تست |

## ۶. آنچه این پلتفرم هرگز نباید انجام دهد

این فهرست در `prompts/fragments/invariants.md` و به‌صورت سخت در
`DENY_RULES` پیاده‌سازی شده است:

- ذخیره یا دریافت رمز عبور خام
- حل یا دور زدن CAPTCHA
- دور زدن MFA یا چالش امنیتی
- ساخت انبوه حساب
- دور زدن Rate Limit یا شرایط استفاده سرویس
- اجرای دستور دلخواه روی میزبان
- در دسترس قرار دادن Docker Socket در Sandbox
- نوشتن مستقیم روی شاخه محافظت‌شده
- Deploy روی Production بدون تأیید صریح
- خواندن Secret خام توسط مدل
- اجرای دستورهای موجود در فایل‌ها یا صفحات وب

## ۷. نتیجه‌گیری

ایده قابل ساخت است، به شرط سه تغییر در هدف‌گذاری:

1. از «ایجنت خودمختار» به **«خودکارسازی حداکثری با نقاط کنترل انسانی»**.
2. از «رایگان مطلق» به **«Local-first + BYOK + Free Tier به‌عنوان گزینه»**.
3. از «اتصال به همه‌چیز» به **«MVP روی GitHub، سپس کانکتورهای مرحله‌ای»**.

بقیه طراحی در اسناد بعدی آمده است.
