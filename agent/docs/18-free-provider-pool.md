# استخر ارائه‌دهندگان رایگان

منبع الهام: [tashfeenahmed/freellmapi](https://github.com/tashfeenahmed/freellmapi) — لایسنس MIT.
پیاده‌سازی: `src/core/free-provider-pool.ts` · تست: `test/free-provider-pool.test.ts` (۲۸ تست)

## چرا این ریپازیتوری

FreeLLMAPI لایه رایگان ۳۴ ارائه‌دهنده را پشت یک endpoint سازگار با OpenAI جمع
می‌کند: طبق ادعای خودش ۴۷۴ خانواده مدل، ۶۳۵ endpoint رایگان، حدود ۷٫۴ میلیارد
توکن در ماه.

چیزی که از آن برداشتیم **پراکسی نیست** — محصول ما پروکسی LLM نیست. آنچه
ارزش برداشتن داشت چهار مکانیزمی است که باعث می‌شود توده‌ای از لایه‌های رایگان
مثل **یک** ارائه‌دهنده قابل اتکا رفتار کند. این چهار مکانیزم دقیقاً همان
شکاف‌هایی بودند که در سند ۱۶ و ۱۷ ثبت کرده بودیم.

| قابلیت در FreeLLMAPI | شکاف ما که بسته شد |
|---|---|
| شمارنده RPM/RPD/TPM/TPD per (platform, model, key) | `GAP-IN-07` حسابداری هزینه، `DC-04` حسابداری توکن |
| fallover خودکار روی 429/5xx با cooldown و چرخش کلید | `GAP-IN-09` سیاست retry، `DC-05` |
| مدل یکپارچه + زنجیره‌های نام‌دار (`auto:<profile>`) | بخشی از `GAP-IN-06` کاتالوگ ارائه‌دهندگان |
| sticky session با handoff note | طراحی نشده بود |
| مرور ToS هر ارائه‌دهنده | `GAP-LG-02` ماتریس انطباق |
| health check دوره‌ای کلیدها | بخشی از `GAP-IN-06` |

## چهار مکانیزم

### ۱. سهمیه آگاه از توکن

سهمیه‌ای که ما تا امروز داشتیم فقط **تعداد درخواست** می‌شمرد
(`tryConsumeQuota` در `model-router.ts` با `rpm`/`rpd`). ولی لایه رایگان
ارائه‌دهنده‌ها با **توکن در روز** سقف می‌گذارد، نه درخواست. نتیجه: یک شمارنده
RPM-only بی‌صدا وارد 429 می‌شود.

`FreeTierQuota` پنج سقف دارد:

```ts
{ rpm, rpd, tpm, tpd, monthlyTokenBudget }   // صفر = نامحدود
```

`tryAcquire` هر پنج سقف را با تخمین توکن می‌سنجد و **دقیقاً می‌گوید کدام سقف
گیر کرده** (`rpm` / `rpd` / `tpm` / `tpd` / `monthly` / `cooldown`)، به‌همراه
`retryAfterHint` درست. بعد از پاسخ، `commitUsage` تخمین را با عدد واقعی
ارائه‌دهنده آشتی می‌دهد.

پنجره‌های دقیقه/روز/ماه **مستقل** رول می‌شوند — تست
`resets minute, day and month windows independently` همین را می‌سنجد.

### ۲. Failover با cooldown و چرخش کلید

وقتی یک کلید ۴۲۹ می‌گیرد، **پارک** می‌شود، نه اینکه دوباره کوبیده شود:

| نوع خطا | cooldown پایه |
|---|---|
| `rate_limited` | ۶۰ ثانیه |
| `server_error` | ۲۰ ثانیه |
| `timeout` | ۱۰ ثانیه |
| `invalid_response` | ۲ ثانیه |

cooldown با خطاهای پیاپی رشد می‌کند و در ۸ خطا سقف می‌گیرد (۶۰ ثانیه → ۸ دقیقه)،
تا ارائه‌دهنده‌ای که نوسان دارد هر ثانیه retry نشود. `invalid_response` عمداً
کوتاه است: آن خطای مدل است، نه ارائه‌دهنده.

قبل از ترک ارائه‌دهنده، **کلید بعدی همان ارائه‌دهنده** امتحان می‌شود
(`rotatedTo`). وقتی همه کلیدها پارک‌اند، تصمیم `cooldown` برمی‌گردد نه شکست
مبهم — تست `reports cooldown rather than silently failing` همین را می‌سنجد.

### ۳. گروه یکپارچه و زنجیره نام‌دار

یک مدل که چهار ارائه‌دهنده سرو می‌کنند، برای فراخوان **یک ورودی** است
(`groupKey`). مسیریابی اول گروه‌ها را رتبه می‌کند، بعد **درون گروه برنده**
failover می‌کند و فقط بعد به گروه بعدی می‌رود. این رفتار را پایدار نگه
می‌دارد: مدل عوض نمی‌شود، فقط ارائه‌دهنده عوض می‌شود.

شش استراتژی مسیریابی:

| استراتژی | معیار |
|---|---|
| `cheapest` | کمترین `relativeCost` |
| `fastest` | `scores.speed` |
| `most-capable` | `scores.capability` |
| `most-reliable` | `scores.reliability` |
| `least-used` | کمترین توکن مصرفی امروز |
| `round-robin` | قدیمی‌ترین `lastUsedAt` |

زنجیره‌های نام‌دار (`coding`، `vision`) با `auto:<name>` در هر درخواست قابل
انتخاب‌اند؛ هر endpoint بیرون از زنجیره با دلیل `not in chain` رد می‌شود.

### ۴. Sticky session

مکالمه ۳۰ دقیقه روی یک مدل می‌ماند. اگر مدل پین‌شده از دسترس خارج شود،
`handoffRequired: true` و یک `handoffNote` برمی‌گردد تا مدل جدید بداند نباید
پاسخ‌های قبلی را تکرار کند. **بدون این، عوض شدن مدل وسط مکالمه یک تغییر رفتار
بی‌صداست** و بدترین نوع باگ برای دیباگ کردن.

## دیوار حالت محاسباتی هنوز حاکم است

`poolAllowsEndpoint` **قبل از هر امتیازدهی** اجرا می‌شود، پس هیچ استراتژی
مسیریابی نمی‌تواند از حالت انتخاب‌شده کاربر عبور کند:

- `local` → هر endpoint ابری رد می‌شود
- `free` → ابری پولی رد می‌شود
- ارائه‌دهنده‌ای که روی ورودی آموزش می‌بیند، برای کار غیر `public` رد می‌شود

تست `no routing strategy can talk its way past the wall` هر شش استراتژی را در
حالت `local` می‌کوبد و اثبات می‌کند خروجی همیشه `local` است.

## یک باگ طراحی که همین کار پیدا کرد

endpointهای لوکال (Ollama، llama.cpp، vLLM) **هیچ کلید API ندارند**. پیاده‌سازی
اول «کلید ندارد» را block سخت می‌گرفت — یعنی حالت Local-first که ادعای اصلی
محصول است، اصلاً نمی‌توانست مسیریابی کند.

راه‌حل: مجموعه کلید خالی به **یک کلید مجازی** (`NO_KEY = "(no-key)"`) تبدیل
می‌شود، تا سهمیه، cooldown و چرخش برای لوکال و ابری یکسان رفتار کنند. تست
مربوطه همین را پوشش می‌دهد.

## آنچه عمداً برنداشتیم

| قابلیت FreeLLMAPI | چرا برنداشتیم |
|---|---|
| Fusion (سنتز چندمدلی با داور) | `DC-22` هنوز باز است؛ نیاز به طراحی قاعده رأی و محاسبه هزینه دارد، نه فقط فن‌اوت |
| فشرده‌سازی پرامپت | به `GAP-IN-03` (context assembler) گره خورده که هنوز طراحی نشده |
| کاتالوگ خودبه‌روزشونده امضاشده | ما کاتالوگ را در دیتابیس نگه می‌داریم؛ فید امضاشده یک تصمیم معماری جداست |
| شبیه‌سازی Ollama / Gemini wire | محصول ما کلاینت LLM نیست |
| کش پاسخ | ریسک نشت داده بین tenant؛ اول `GAP-SE-06` باید بسته شود |
| پراکسی `/v1` | خارج از دامنه محصول |

## نکته انطباقی

`staleTosReviews` endpointهایی را که مرور ToSشان قدیمی‌تر از ۹۰ روز است (یا
تاریخشان قابل پارس نیست) علامت می‌زند. لایه رایگان هفته‌ای عوض می‌شود؛ یک
ماتریس انطباق تاریخ‌گذشته از نبودنش خطرناک‌تر است، چون اعتماد کاذب می‌سازد.

`ProviderTos` این واقعیت‌ها را کنار خود endpoint نگه می‌دارد، نه در یک سند
دور — تا مسیریابی بتواند **به‌خاطر اصول** رد کند، نه فقط به‌خاطر سقف.
